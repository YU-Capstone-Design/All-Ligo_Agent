> 각 안건의 "사실"은 코드/서버에서 직접 확인한 것이다. 결정되면 `결정:` 줄을 채운다.

## 1. 생성된 영상을 앱에서 "바로 보이게" — S3 링크 vs YouTube 링크

**배경**: 설계과제 발표에서 교수님이 영상이 (지도 앱처럼) 바로 보이게 하라고 지적하심. 요구는 "보이게만" 하라는 수준.

**사실**
- Was 미리보기 API 는 이미 두 링크를 **모두** 내려준다: `s3VideoUrl`(S3), `uploadVideoUrl`(YouTube).
- 시점 차이: S3 링크는 **생성 직후(예약 5분 전)** 부터, YouTube 링크는 **예약 시각 업로드 이후**부터 있다.
- S3 영상은 브라우저에서 바로 재생되는 형식(H.264, faststart, `video/mp4`)으로 올라간다. 버킷이 영상도 공개 읽기인지는 미확인.
- YouTube 는 `unlisted`(링크가 있어야 보임, 임베드 가능)로 올라간다.

**논의할 것**: 앱이 어느 링크로 보여줄지.
- (A) S3 링크로 바로 재생 / (B) YouTube 링크로 재생 / (C) 업로드 전엔 S3, 업로드 후엔 YouTube

## 2. 서버 간 인증 (선택 사항)

**사실**: Agent API 는 인증이 없고, `<AGENT_HOST>` 는 인터넷에서 누구나 접근할 수 있다(같은 상위 도메인의 서브도메인이라는 사실은 보안 경계가 아님). Was 도 Agent 호출에 인증 헤더를 보내지 않고, Was 의 콜백 엔드포인트도 인증이 없다.

**제안**: 공유 키 하나를 정해 양방향에 쓴다. Agent 는 키가 **설정된 경우에만** 검사하도록 만들어, 키를 넣기 전까지는 지금처럼 동작(연동이 깨지지 않음).

**논의**: 발표 전에 적용할지.

## 3. 같은 계정에서 같은 시각 예약 막기 ⭐ (필수 안건)

**사실**
- 현재 Was 는 **한 홍보 안에서만** 같은 요일·시각 중복을 막는다. 같은 계정의 **다른 홍보끼리**는 같은 시각 예약이 가능하다.
- Agent 는 이미지 생성을 GPU 에서 한 번에 하나씩 처리한다. VIDEO 1건에 실측 40~90초.
- Was 는 예약 시각에 결과가 아직 없으면 그 회차 업로드를 다시 시도하지 않는다. 같은 시각 예약이 몰리면 뒤 순번이 5분 안에 못 끝날 수 있다.

**제안**: 같은 계정에서 같은 요일·시각(분 단위) 예약을 생성·수정 시 거절한다. 다른 계정끼리의 충돌은 이번에는 고려하지 않는다.

**논의**: 어느 API(홍보 생성/수정)에서, 어떤 에러로 막을지. 담당자.
